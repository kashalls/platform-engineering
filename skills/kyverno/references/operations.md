# Running Kyverno in production

## Components

```bash
kubectl get pods -n kyverno
```

Four Deployments, each with a distinct failure surface:

| Deployment | Owns | Symptom when down |
|---|---|---|
| `kyverno-admission-controller` | validate/mutate webhooks | Admission blocked or unenforced |
| `kyverno-background-controller` | generate, mutateExisting | Generated resources never appear |
| `kyverno-reports-controller` | PolicyReports | Reports go stale |
| `kyverno-cleanup-controller` | CleanupPolicy TTL | Objects never cleaned up |

When "the policy did not fire", match the symptom to the controller first —
enforcement and generation are different processes.

## Rollout sequence

1. Write the policy and test locally: `kyverno apply` + a `kyverno test` file.
2. Deploy with `validate.failureAction: Audit`.
3. Read PolicyReports for a full business cycle — batch jobs and CronJobs surface
   violations that steady-state traffic does not.
4. Fix or except the legitimate violations.
5. Flip to `Enforce`.

```bash
# Failing results grouped by policy, to size the blast radius before enforcing.
kubectl get policyreport -A -o json | jq -r '.items[].results[]?
  | select(.result=="fail") | .policy' | sort | uniq -c | sort -rn
```

Skipping step 3 is how a policy rollout becomes an incident.

## Exceptions

`PolicyException` is an object, not an annotation:

```yaml
apiVersion: kyverno.io/v2
kind: PolicyException
metadata:
  name: legacy-app-exception
  namespace: legacy
spec:
  exceptions:
    - policyName: require-team-label
      ruleNames: [check-team-label, autogen-check-team-label]
  match:
    any:
      - resources:
          kinds: [Pod, Deployment]
          namespaces: [legacy]
          names: [legacy-app-*]
```

Two things that catch people:

- **List the autogen rule names too.** Excepting `check-team-label` alone leaves
  `autogen-check-team-label` enforcing against Deployments — the exception looks
  broken when it is merely incomplete.
- **Check that exceptions are enabled and where they may live.** The admission
  controller's `--enablePolicyException` and `--exceptionNamespace` flags decide
  this; restricting exceptions to one namespace stops tenants self-exempting.

Prefer a narrow exception with an expiry ticket over widening the policy. An
exception is visible and auditable; a weakened policy is neither.

```bash
kubectl get policyexceptions -A
```

## Reports

```bash
kubectl get policyreport -A
kubectl get clusterpolicyreport
kubectl get policyreport -n <ns> -o json | jq '.results[] | select(.result=="fail")'
```

Reports are generated by background scans and by admission. They can be large in
a big cluster — the reports controller is usually the first component to need
more memory.

Background scan caveats:

- Only policies with `background: true` are scanned.
- Rules referencing `request.userInfo`, `request.operation`, or `request.roles`
  cannot run in background and will error.
- A scan reflects the policy at scan time; after changing a policy, wait for the
  next interval before trusting the report.

## Performance

Kyverno sits in the admission path of everything it matches. Cost controls:

- **Narrow `match` aggressively.** Matching all kinds in all namespaces makes
  every API write pay for policy evaluation.
- **Use `preconditions`** to bail out cheaply before expensive evaluation.
- **Avoid `apiCall` context in hot paths** — it makes a live API request per
  admission review.
- **Set `background: false`** on policies that only make sense at admission.
- Kyverno generates its webhooks from installed policies, so an over-broad match
  literally widens the webhook's `rules` and increases cluster-wide latency.

```bash
kubectl get validatingwebhookconfigurations -l webhook.kyverno.io/managed-by=kyverno -o yaml \
  | yq '.items[].webhooks[].rules'
```

Reading the generated webhook rules is the honest measure of how much traffic
your policies intercept.

## Break-glass

`failurePolicy: Fail` plus an unavailable Kyverno blocks every matching write —
including the writes needed to fix Kyverno. Know this before you need it:

```bash
# What Kyverno is intercepting.
kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations \
  -l webhook.kyverno.io/managed-by=kyverno

# Break glass: remove the webhooks. Kyverno recreates them when healthy.
kubectl delete validatingwebhookconfigurations -l webhook.kyverno.io/managed-by=kyverno
kubectl delete mutatingwebhookconfigurations -l webhook.kyverno.io/managed-by=kyverno
```

Preventative measures: run at least two admission controller replicas with a PDB,
keep `resourceFilters` excluding `kube-system` and Kyverno's own namespace
(the default), and consider `failurePolicy: Ignore` for policies that are
advisory rather than security-critical.

The tradeoff is explicit: `Ignore` means a Kyverno outage silently stops
enforcement. For a policy that exists to satisfy a compliance control, `Fail` is
correct and the mitigation is availability, not weakening the policy.

## Cleanup policies

```yaml
apiVersion: kyverno.io/v2
kind: ClusterCleanupPolicy
metadata:
  name: cleanup-completed-jobs
spec:
  match:
    any:
      - resources:
          kinds: [Job]
  conditions:
    all:
      - key: "{{ target.status.succeeded || `0` }}"
        operator: Equals
        value: 1
  schedule: "0 * * * *"
```

A cron-scheduled deleter. It needs explicit RBAC to delete the target kind, and
it is genuinely destructive — test the match with `kyverno apply` against real
manifests before scheduling it.
